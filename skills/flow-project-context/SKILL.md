# 项目事实驱动流程

套件仅提供通用流程、标准记录和校验，不提供项目事实。项目的业务含义、技术栈、启动命令、端口、测试框架、接口、账号、部署环境、规范与交付条件必须主动调查。套件示例和模板不是默认项目事实。

先读 [项目上下文协议](../../docs/project-context.md)。运行 `discover --workspace <工作区> --area <领域>` 定位候选与过期记录；这是只读索引，不代表材料已读或命令已验证。只收集当前动作需要的信息，不用无关缺项阻断工作。

1. **发现**：查已有 project 配置和项目上下文，读业务仓 AGENTS/README/CONTRIBUTING、包脚本、构建/测试配置、CI、部署配置和相关代码；按项目明确引用再查文档、工单、设计、测试原件及可用连接器。不要扫描私人目录、密钥文件或无关共享盘。
2. **核实**：区分声明、代码现状和实际观察。脚本名称不证明覆盖，环境地址不证明可连接，端口开放不证明是目标服务。对本次所需能力做适当的只读检查或已授权验证，记录依据；不为了“收集”启动服务、修改数据或登录未授权系统。
3. **解决冲突**：用户本次明确指令决定目标与授权；项目规则决定项目约束；代码/配置描述现状，工单/设计描述期望。按领域核对，不用一个固定优先级抹掉矛盾。只有影响当前行动且无法自行查清的决定才问用户，问题附已查证据与选项。
4. **应用**：将已核实结果落到业务项目的配置/材料中，按本协议记录来源及绑定。启动/测试命令必须从真实项目提取，再验证 argv/cwd/前置；不能照抄套件 npm、端口、health 路径或测试框架。有等价现成能力优先适配，不另建一套。
5. **复查**：相关来源文件、配置、依赖、分支规则或部署版本变化时重核对应事实；动态来源在实际操作前复核。只补受影响部分，不让用户反复确认未变化的决定。

代码和配置修改前按用户既有授权推进；本次仅查看时只输出调查结果，不写项目上下文。没有收集到的保持 unknown；推测标 inferred，不能变成 verified。输出简短说明采用了什么项目事实、剩余缺口及下一步，不把内部表格丢给用户填写。

按 [测试复用协议](../../docs/test-reuse.md) 先查项目已有测试代码、事实和执行经验，核对变化后复用有效方法，避免重复发现和导入；成功路径在已授权范围内沉淀回项目。用户明确要求重测必须真实执行，动态环境不能仅凭本地摘要复用结果。每轮反馈实际复用项、重新核实/执行项及原因。
