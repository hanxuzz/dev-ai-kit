# 范围和影响

先读映射的规格及原始来源、代码仓规范和相关代码。范围内每条 R 要有来源、可观察验收；明确不做单独列出。已有 Spec 不改名，不整篇覆盖。
有冲突先写问题，questions=open。用户带来实际答复后记录，全部解决才能继续；不通过删掉问题来解除门禁。

影响分析不能只列路径：按需核对接口调用方、数据与历史记录、权限状态、异常并发、缓存异步、交付先后、回退条件。不适用写原因；不能为了填表发明影响。
“修改”路径必须存在；新增路径标明新增。引用读过的代码依据，保留明确不改内容。

使用 requirements.yaml 表达 R/title/sources/acceptance 和 out_of_scope，与规格保持一致。cross-system 填 assessments；quick 可在同一 brief 中解释。
通过 prepare 保存草稿。结构校验只是第一关；语义及范围必须由本次用户确认，不能让脚本代替需求理解。
