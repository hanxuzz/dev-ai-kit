# 针对实际代码审查

这是开发闭环的必需步骤，不要求用户额外调用。只读审查不修改代码；已授权开发任务内发现问题可以修复后重新验证。不得把另一位审查者或用户未做过的检查记为已做。

1. `quality inspect --target <任务>` 查看行为约定、参考实现、从 start 起变化的文件、参考变化和旧审查失效原因。读取原需求及来源、项目规则、实际 diff、相关完整函数和调用方。inspect 是文件指纹差异，不是完整文本 diff；Git 现有未提交修改可能早于本任务，须和开始时记录区分，不回滚他人改动。
2. **需求一致性**：逐条核对当前→目标行为、触发/默认/异常、明确不改项及真实验收。测试断言回到原需求和正式用例，不能仅按新实现反推断言。记录实现位置和实际验证依据；漏项、额外功能或业务误解都要处理。
3. **项目适配**：对照实际参考代码核对架构层次、命名、错误处理、接口封装、状态管理与风格。搜索已有同类能力及调用方，判断是否重复实现。新组件、公共抽象、依赖或契约需解释现有能力不能满足的原因；不因偏好重写项目。
4. **影响与回归**：阅读共享代码的使用方，验证保留行为及 regression_cases；检查新增依赖、公共接口、数据/权限变化、额外重构和大面积格式化是否已纳入范围。测试、lint、类型检查按项目真实能力运行，不统一要求某套工具。不相关故障与本次缺陷分开说明，不能删检查绕过。
5. 修复明确缺陷后重跑受影响验证，再审查当前代码。新增业务决定或扩大范围先走变更。仍有未解决项时不记录通过。
6. 用 `quality review --input <报告> --by <实际审查者> --expect <revision>` 记录逐条结论，再 finish。格式见 [开发质量协议](../../docs/development-quality.md)。报告不是用户验收，也不替代测试证据。之后代码/依据变化会使审查失效。

小改动允许简短证据，不允许空泛“符合最佳实践”。报告内部保存，面向用户只说明需求如何满足、复用了什么、验证及剩余风险。
