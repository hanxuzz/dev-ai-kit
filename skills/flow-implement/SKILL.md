# 按任务实施

开始前按 [flow-project-context](../flow-project-context/SKILL.md) 主动核对本步骤依赖的项目事实，将核实结果应用到项目配置与材料；来源变化只复核受影响部分，不拿套件示例代替实际项目约定。

先读 assist resume、对应仓库规则和当前 Git 现状；按需展开 status --full。原始请求已有明确实施授权时复用，与已确认需求存在业务变化时，即使最新请求明确也先按 docs/trust.md 展示差异并取得二次确认；不以旧连续授权覆盖。用 docs/trust.md 判断本轮是只读、一步还是明确授权连续执行。

1. 按 [开发质量协议](../../docs/development-quality.md) 核对当前版本行为约定、参考代码、复用取舍、调用方影响及保留行为，缺少时先调查并用 quality plan 补齐。明确原始授权可复用，不让用户填写内部记录。核对任务依赖和文件范围。原始设计与规格矛盾先澄清，不擅自选一份。
2. 视觉还原查看设计或截图；文案/字段修复可以使用已确认文字和现有页面，不能一律索要 Figma。
3. 按团队策略确认当前分支。不符合时按现有授权创建/切换或询问；auto_create=false 不允许在错误分支上凑合修改。
4. `start --target TASK-N --expect <revision>` 保存修改前快照。已经 doing 的任务从快照和交接继续，不再次 start 重置证据。
5. 每完成有意义的修改，读实际差异并对照行为约定和参考实现，核对复用、风格、调用方与保留行为；用 quality inspect 发现变化与审查缺口。按任务改动并用项目已有命令验证新增行为及回归用例。若改动需要扩展到范围外，先说明原因、走变更确认；不顺手改格式或删除别人的工作。
6. `run --check <名> --expect <revision>` 收集本地命令证据；仅传入实际满足且已授权的 --ready 前置。命令缺失可按计划做真实人工验收，不伪造结果。
7. 验证后必须执行 [flow-code-review](../flow-code-review/SKILL.md)，按实际代码完成需求一致性与项目适配审查，用 quality review 记录。测试和审查证据都有效后 `finish --target TASK-N --expect <revision>`。读取 next 作为报告，不自动执行下一步。

失败先诊断，不盲目重跑有副作用命令。环境受阻时保留未完成状态，记录 blocker/handoff。连续执行遇到变更范围、确认、不可用依赖或不明失败即停止。
完成用户授权的工作后说明修改、验证和残余风险；提交和推送按用户明确要求执行；已有对应授权直接复用，不重复询问，具体语义见 docs/trust.md。

本轮结束必须按 [进度反馈协议](../../docs/progress-feedback.md) 主动反馈最新结果、进度和具体下一步责任方；使用最新 progress，结合真实操作与本轮授权说明，不能仅报完成或要求用户自行查询。

测试轮不直接进入实施。先记录问题并继续可独立场景，结束并交付报告后，才能另开明确授权的修复轮；不能套用旧开发授权自行修复。进入实施时，遵循 [修复与续测协议](../../docs/test-automation.md#测试发现缺陷后的修复与续测)：修复沿用全部开发依据与审查要求，本地相关服务重启并确认就绪后恢复原测试；已完成任务通过变更流程关联修复任务，不直接改状态或略过回归。
