# 按计划实现

按 `docs/runtime.md` 做开始检查，并读 `docs/trust.md`。

`questions` 为 `open`，或 `06-plan.md` 不存在时，停止，不要改业务代码。

## 开始前

1. `current` 指向的需求不明确，或目录多于一个：让用户选定，不要默认第一个。
2. 读该代码仓的 `AGENTS.md`（没有就读 `README`）。把红线列在对话里。没有这类文件就说明「无项目约定」，改代码时再读套件 `docs/code-style.md`。项目里已有的写法优先于这份说明。
3. 读 `06-plan.md`。用户点名的任务若标了「不执行」，跳过并说明原因。
4. 用户没点名任务时，只做第一个未勾选的任务，然后停下。
5. 当前 git 分支是 `main` 或 `master` 时，先告诉用户，等用户明确说就在这个分支改，再动代码。

## 改代码

- 只改这个任务写明的文件。标成「修改」的路径不存在就停止。标成「新增」的路径可以新建。
- 不顺手改相邻格式、注释或重构。发现可以另做的清理，写在对话里，不要改。
- 新增或改到的注释按 `docs/code-style.md`：解释为什么和副作用；项目已规定注释语言或位置时以项目为准。
- 任务里的验证命令先跑一遍。已经失败则先报告，不要把失败算到这次改动上。
- 步骤按 `- [ ]` 做完就勾上。不要跳过验证那一步。

## 怎样才算做完

声称这个任务完成之前，必须在本轮对话里运行任务写明的验证命令，看退出码和输出。没跑过就不能说通过。命令为空或环境没配：按 `skills/flow-test/SKILL.md` 说明缺什么，任务保持未完成。做完的标准见 `docs/practices.md` 里的完成定义。

同一条验证连续失败 3 次：停止，把三次现象写进该需求的 `blocker`，不要换一种猜法继续改。

做完用户点名的那一个任务就停。不要接着做下一个，也不要提交，除非用户同时说了提交。
