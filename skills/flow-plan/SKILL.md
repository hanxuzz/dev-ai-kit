# 任务计划

读映射规格、影响点和团队规则。questions=open 不编最终计划。每条范围内 R 都要有任务，明确不做不能混进任务。

建立稳定 TASK 编号；按仓库拆分，depends_on 可跨仓引用，不能循环。每个任务写目标、文件范围、检查名或真实人工验收条件。接口先明确契约，再安排依赖方。
Markdown 解释实施方案，tasks.yaml 表达执行图；保留原有计划，不从复选框猜测已完成。
用 cases.yaml 对应验收：检查命令必须实际覆盖该 R；没有自动化就写明确人工步骤，不因为项目有 npm test 就声称自动覆盖。

`validate --ready` 验证覆盖和依赖。把范围、明确不做、任务及验收汇总给用户；用户已授权当前明确方案时可记录该事实，否则等待确认。
`confirm --by <实际确认人> --note <确认依据>` 绑定当前版本。写完计划或确认计划本身不代表获得改代码、提交或部署授权。

开工计划必须包含 [开发质量协议](../../docs/development-quality.md) 的任务 development：逐条需求当前/目标行为、必须保持行为、实际参考实现、复用取舍、调用方影响和回归用例。先搜索同类功能和已有能力，再决定新增结构；新增依赖、抽象或公共接口说明必要性。用 quality plan 自动绑定真实参考文件，不拿模板路径和示例值填表。
