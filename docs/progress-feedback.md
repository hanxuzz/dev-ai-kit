# 每轮结束后的进度与下一步

套件必须让用户知道“这轮做了什么、需求到哪了、下一步谁来做”。这不是要求用户主动查询，也不是每次展示完整看板。

## 默认反馈

所有处理需求的技能在一轮授权工作结束、遇到阻塞或需要业务决定时，都要读取最新 progress 并面向用户简短说明：

1. **本轮结果**：只说本轮实际完成的动作与验证，不把历史完成项当成本轮工作。
2. **当前进度**：当前阶段、任务已完成/总数，必要时补充测试与审查是否仍有效。任务数量不是工时百分比；任务数尚未明确时直接说仍在准备，不编完成比例。
3. **下一步**：说明具体工作、由 Agent/用户/外部人员哪方推进；需要用户时列出具体决定或材料及回复示例。引用实际需求内容，不把命令、revision 或 TASK 编号当成用户作业。

这些信息可以合成两三句话，不强制固定标题和长清单。原规则“每个技能结束允许读取 next”改为必须检查并主动反馈；连续授权内应继续执行，不把每个内部命令都变成一次停顿。

例如（示意，必须替换为真实结果）：

> 本轮已完成订单筛选，复用了现有查询组件，相关检查通过。当前任务完成 2/3，还剩空结果展示。下一步由我在既定范围内补齐并验证，你暂时不用操作。

只有本轮确有连续执行授权且 Agent 正在继续时才能说“由我继续”；如果用户只授权一步，应明确“本轮按单步要求结束，下一项是……，需要继续时可说……”。不要一边宣布继续，一边结束对话等待用户。

## 不同停点怎么说

| 状态 | 下一步说明 |
|---|---|
| 材料或项目依据缺口 | Agent 先读已有材料自行补齐；只有查不清的业务决定才问用户 |
| 业务问题或范围变化 | 展示实际问题/新增差异和影响；原请求已明确的决定直接复用 |
| 开发中 | 说明当前任务和剩余工作，按单步/连续授权判断继续或交回 |
| 测试失败、证据过期、缺审查 | 说明哪项缺失及先处理什么，不把排障一概推给用户 |
| 环境阻塞 | 说明已完成部分、具体缺口、谁能解决，以及还能独立推进的工作 |
| 等待验收 | 给出实际观察入口和验收要点；用户接受后才标记验收完成 |
| 需求已完成 | 明确本需求无需继续开发；提交、推送、发布按真实 Git/部署结果另报，不从 done 推断 |

若“业务问题待确认”状态里没有具体问题，Agent 应先读取问题原文，不能只让用户回复泛泛的“确认”。

## 机器输出与时效

`assist resume/review` 包含 progress。CLI 的状态更新、测试执行、quality plan/review、用例应用、next/status 及安装应用后也附带最新 progress。begin/change 仅预览时不声称应用后的进度。摘要是只读结果，不授予执行权限，也不自动创建提交或部署。

progress 包含阶段、任务计数、当前有效检查/用例/审查计数、进度原因、验证缺口、下一步职责及可选回复示例。recent_completed 是历史已完成项，latest_record 是最近记录，均不等于“本轮完成”。current_tasks 来自真实 doing 状态。

历史 last_result: passed 不会直接计为当前通过：代码、需求、检查配置、环境变化或确认失效会重新核对适用性。任务已登记完成但证据失效时，任务数保持历史事实，同时提示补验证；不能因此显示已验收或“全部结束”。

Git/部署默认 not_inspected；Agent 若要报告提交、推送或发布，应读取真实状态或本轮操作结果。每个 CLI 操作只附加摘要，不改变原权限和退出码；写入成功但摘要读取失败时，明确保留操作结果，提示重读状态，不能误导 Agent 重复执行写入。

安装过的业务项目需要升级套件规则，才能获得“必须主动反馈”的新指引；仅更新套件源码不会自动覆盖各项目已有规则。
