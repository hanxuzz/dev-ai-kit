# 项目上下文协议

## 套件与项目的边界

套件维护通用流程、标准记录格式、权限边界、证据校验与扩展入口。业务项目维护自己的事实与策略。实例、示例端口、启动脚本、Playwright 配置、健康接口都只是演示，不能在发现阶段自动复制为项目设置。

| 当前动作 | Agent 主动收集 | 应用位置 |
|---|---|---|
| 安装/接管 | 仓库结构、文档落点、已有流程与配置 | project.yaml、project.local.yaml、docs/team |
| 需求分析 | 业务术语、角色、规则、原始工单、设计、现有行为 | 需求材料、sources、R 与验收映射 |
| 开发 | 语言/框架、构建、目录边界、分支与编码规范 | 项目配置、任务文件范围与依赖 |
| 本地启动 | 实际命令、工作目录、端口、环境变量名、依赖、就绪方式、停止方式 | runtime.services 的说明及项目已有启动/测试配置 |
| 测试 | 已有框架、脚本、fixtures、隔离方式、报告格式、覆盖及人工项 | runtime.checks、cases、实际测试文件 |
| dev 验证 | 目标地址、部署版本核实方式、账号来源、网络条件、测试数据边界 | runtime.environments、requires、用例前置与证据 |
| 交付 | 项目验收、CI、回归范围、发布/回退约定 | 交付材料、检查配置和验收记录 |

不要求每个项目都具备数据库、浏览器、微服务、云环境或某种测试框架。缺什么只影响依赖它的步骤。先利用已存在能力，需要补建时按真实项目约束实现。

## 主动收集顺序

1. 已有项目上下文及配置：先复用，核对新旧差异。
2. 业务仓规则、README、构建/依赖声明、脚本、CI、测试/部署配置以及相关代码。
3. 项目指向的工单、设计、需求、接口和测试材料；使用当前可用且已授权的文档工具、连接器、浏览器等读取正文。
4. 适当的实际观察：核对命令是否存在、测试是否实际覆盖、服务身份与健康、部署版本。启动、登录、远端写入等仍按用户授权执行。
5. 查不到或冲突时才询问具体缺口；不要求用户填写一整份调查问卷。

候选文件存在、配置字段存在、链接可见、脚本名叫 test 都不构成 verified。不能把示例值、推测或工具返回的猜测当成项目事实。

## 可追踪记录

项目的 `<文档根>/team/project-context.yaml` 保存经过整理的非敏感事实；不写进套件源码。只在本次授权包含配置或整理时写入。示例结构如下，值须替换为实际核实内容：

```yaml
schema_version: 1
facts:
  - id: testing.unit
    area: testing
    status: verified
    value: 项目现有单元检查，覆盖领域逻辑，不覆盖页面交互
    verified_by: 实际核实者
    verification: 已读取真实脚本、测试文件，并执行该检查；结论见需求证据
    sources:
      - kind: file
        repo: app
        path: package.json
        sha256: '<discover 返回的实际摘要>'
      - kind: file
        repo: app
        path: tests/unit/example.test.ts
        sha256: '<实际文件摘要>'
    binding: [runtime, checks, unit]
    applied_sha256: '<discover 返回的配置摘要>'
```

area：overview/conventions/development/testing/environments/business。
status：verified/inferred/unknown/conflict/not-applicable。未知项注明缺什么，冲突项列出相互矛盾的依据；不适用说明原因。所有已核实结论记录核实者和方法，重要的动态事实写核实时间。

来源类型：file 使用 repo/path/sha256（repo: workspace 表示工作区根）；external/user/observation 使用 reference、checked_at，记录链接、明确用户决定或非敏感观察引用。不得包含账号正文、令牌、原始私密响应；只保存凭证变量名或条目引用。机器路径放 project.local.yaml，不进入共享项目事实。

binding 是 project.yaml 键路径数组；applied_sha256 将事实与其实际应用配置关联。业务事实不一定对应配置，可在 verification 说明关联的需求/任务位置。不得仅写一份背景文档而继续用套件示例运行。

## 只读发现与过期检测

```text
kit discover --workspace <工作区> --area testing
kit discover --workspace <工作区> --area environments
```

命令有限扫描工作区与已配置仓库的常见资料位置，返回文件路径与摘要，不输出内容、不执行脚本、不读取环境变量值，也不写配置。每个根最多列出 60 个候选；这不是完整资料清单，Agent 应根据项目引用补读相关文件。

已有记录的文件缺失/摘要变化、配置绑定变化、未核实状态会列出问题；没有相关记录则提示收集。外部和实际运行观察属于动态来源，使用前由 Agent 复核。脚本不自动联网，也不能证明记录作者的判断正确。

这不是“安装时填表一次就永久可信”，也不是要求每次从头调查。Agent 必须在当前动作前核对所依赖事实，变化时更新对应记录与配置，必要时使相关计划/验证失效。没有关联的信息不会成为统一全局门禁。

## 框架与能力适配

测试优先采用项目真实框架。JUnit 是本版逐条结果支持的交换格式，不要求把所有项目改成 Playwright；原生报告不兼容时，可在项目中增加保留通过/失败/跳过语义的适配器。暂无可靠适配时说明自动化缺口，不假装支持。

本地启动可由现有任务、容器或测试框架管理；按项目选择，不固定 npm、3000 或 /health。dev 的就绪和部署版本核实方式同样由项目提供。任何适配都应保留通用流程中的需求映射、真实执行证据与环境边界。
