# 开发一致性与项目质量协议

目标是让代码符合原始需求、保留既有行为、沿用项目能力和规范。套件校验映射、来源和证据时效；语义正确性、架构合理性仍需要 Agent 阅读实际代码。填写字段不能代替调查或审查。

## 生效与兼容

新安装默认 `development.require_contract: true`。既有项目配置保持不覆盖；升级后 Agent 主动检查该字段，在用户已授权接入新流程时添加并说明生效范围。开启后当前任务需要补开发依据，已完成任务缺审查时需核对后记录，不需要重写已正确实现的代码。只读请求不改配置。

旧配置缺此字段或显式 false 时保留原运行行为；任务一旦包含 development，仍启用该任务的依据和审查检查。Agent 不得为了通过检查关闭开关或删除 development。开发请求始终遵循技能流程，兼容模式不代表可以略过真实需求与代码核对。

## 开工前：行为与实现依据

通过原需求、实际代码和项目事实明确当前行为、目标行为、必须保持的行为。场景需要的触发、默认、异常、权限等写进实际约定；不适用不编造。用户要求明确时复用原始授权，内部整理不是新的确认仪式。

每个任务在 tasks.yaml 的 development 中保存轻量记录：

```yaml
behaviors:
  - requirement: R1
    current: 保存成功后显示旧提示
    expected: 保存成功后显示已保存，失败提示沿用原逻辑
    cases: [T1]
approach: 只修改已有消息资源，通过原保存流程引用
references:
  - repo: app
    path: src/messages.ts
    reason: 沿用现有消息定义和命名方式
reuse: 复用现有通知组件及消息资源，不新增提示组件
impact: 检查该消息的全部引用，确认未被其他业务共享
preserve: 保存请求、失败提示和页面跳转不变
regression: 按 T2 验证原失败路径；既有测试覆盖请求次数与跳转
regression_cases: [T2]
```

示例文件与用例必须替换成真实项目内容。references 可引用其他仓库的实现；新项目没有可比代码时引用真实规则或设计文件并说明原因。记录查找与不复用的具体理由，不强行复用不适合的能力。

```text
kit quality plan --workspace <工作区> --target TASK-1 --input <开发依据.yaml> --expect <最新revision>
```

命令核对需求/用例映射和参考文件，自动记录参考摘要，并通过现有 prepare 更新任务，纳入范围确认和变化追踪。它不会执行 Git 写入或改业务代码。所有必需任务依据整理好后用原始明确请求或实际确认运行 confirm，再 start；参考在开工前变了需重新调查。

`assist begin` 仍可生成 quick 的最小材料，但不会凭空生成项目参考代码。新安装启用本协议时，Agent 接着调查并调用 quality plan，随后复用已有明确授权，无需用户补内部记录。

## 开发中：持续对照

每个有意义的改动后，Agent 对照行为、实际参考实现、复用选择和调用方。发现扩大范围、公共行为变化、新依赖或额外重构时先评估，再按已有授权处理；新增业务决定才询问。文件少不等于影响小，共享函数的一行修改也需要核对使用方。

```text
kit quality inspect --workspace <工作区> --target TASK-1
```

只读返回从任务 start 开始变化的文件、参考变化和审查缺口。不会生成代码正确性结论；Agent 必须读 Git 差异和相关代码，并分清任务开始前已有的修改。参考变化可能正是本任务对该文件的修改，审查时需要辨明。

## 完成前：双重审查与真实验证

先按项目实际工具验证新增行为与保留行为；再按 flow-code-review 阅读真实差异，核对需求一致性及项目适配。简短报告格式：

```yaml
requirements:
  - id: R1
    implementation: app/src/messages.ts 的保存成功消息，原保存入口继续引用
    evidence: T1 本轮检查结果；具体证据见 run 输出
reuse: 沿用现有通知组件，无重复封装
style: 与相邻消息定义、命名和导出方式一致
impact: 已核对消息引用，未改变公共接口或其他业务提示
regression: T2 失败路径及原保存行为已验证
findings: []
```

只有实际核对且无未解决问题时才记录：

```text
kit quality review --workspace <工作区> --target TASK-1 --input <审查报告.yaml> --by <实际审查者> --expect <最新revision>
```

审查绑定当前仓库内容、任务/需求、参考文件和项目规范。代码或依据变化后需重查；报告包含逐条实现及验收依据，不能填“已经检查”代替内容。finish 和 complete 都检查审查时效；finish 还检查关联的行为与 regression_cases 的真实通过证据，不能只在报告里声称已验证。若把 dev 验收列入该任务约定，任务也须等待该验证；通常将部署后验收放在独立验收阶段，开发任务绑定本地可执行用例。审查通过不能代替测试通过，测试通过也不能代替审查。

默认按仓库内容保守失效，多任务连续修改后可能需要对先前任务重新核对；支持在 done 状态刷新审查，保留已完成实现。项目事实核实、审查和用户最终验收是不同记录，不互相冒充。
