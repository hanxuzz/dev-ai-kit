# 哪些项目适合

套件假设：有人提需求，有现成代码可对照，改动能用「给定 / 当 / 则」判断做对没有，并且有人确认之后才改代码。

## 比较适合

- 前后端分开的业务系统。Cursor 打开的是包住两个仓库的文件夹，例如 `psl/frontend` 和 `psl/backend`。
- 只有一侧也行，只要这个文件夹里有一个带 `.git` 或构建文件的代码目录。
- 需求来自会议、网页、设计稿或文档，而且能指出要改现有哪一块。
- 团队里有人看问题清单、有人改代码、有人补测试。三个人可以是同一人，但确认和改代码不要混成一步。
- 项目自己已有启动命令、测试命令或代码规范。套件把它们记在 `project.yaml` 和该仓库的 `AGENTS.md` 里，不另外发明一套。

## 不太适合

- 从零开始、还没有代码目录的想法。套件要先对照现状，没有仓库就停。
- 把某一个代码仓库本身当作 Cursor 的根目录打开。安装会拒绝，因为文档和两个仓库会搅在同一次提交里。先在外面建一个父文件夹，把仓库放进去。
- 只要一句口头需求就直接改完、不许中途停下来问人。问题没确认时，套件不允许写开发顺序。
- 探索性脚本、一次性数据整理、没有「做对了是什么样」的研究草稿。
- 必须把录屏、密钥放进 git 的流程。套件把原件放在共享目录，口令只记条目名。
- 用套件仓库自己当业务项目。`dev-ai-kit` 只提供技能和模板。

## 能用，但要降低预期

- 没有转写工具时，录屏这一步会停，其余步骤仍可从链接和文档开始。
- 没有只读数据库账号、没有浏览器插件时，对应用例标成 `manual`，不要假装已经测过。
- 代码仓里已有提交规范、注释规范和分支策略时，以那个仓库为准。套件的 `docs/code-style.md` 只在项目没写的时候使用。
