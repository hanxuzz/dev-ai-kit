# 自动化测试接入

开发者说“根据需求补测试”或“导入测试人员的文件，在本地/dev 执行”，Agent 应进入 flow-testing，主动解析原件、规范化、选择执行层次并运行验证。用户不必先转换文件。

执行前先按 [项目上下文协议](project-context.md) 发现真实启动方式、测试框架、报告和环境，以下示例不是默认项目配置。

## 任意格式原件与统一格式

任意格式是 Agent 的接入责任，不代表 Python 核心内置全部解析器。Agent 使用当前可用的文档、表格、PDF、OCR 等能力，遇到无法读取内容必须报告缺口。原件不覆盖；从每个原件生成规范化 YAML，逐条保留 source_location。多个原件分别导入。

```yaml
cases:
  - id: QA-ORDER-001
    external_id: TC-001
    title: 订单列表仅显示所选状态
    requirements: [R1]
    repo: frontend
    source_location: QA.xlsx / 订单 / 第 5 行
    preconditions: 测试账号可访问订单列表
    test_data: 独立测试租户，已有两种状态的订单
    steps:
      - 打开订单列表
      - 选择已完成状态
      - 检查列表中每条记录的状态
    expected: 只显示已完成订单，无结果时显示空态
    kind: auto
    check: order-api-local
    test_name: orders::filters_completed
```

必需字段：id/title/requirements/repo/steps/expected/kind。转换任意原件时 source_location 必需。前置与数据不适用可写明，不编造。测试数据使用合成数据或变量引用，原件中的凭证及客户隐私不能复制进共享用例。`external_id` 保留原始编号；合并多文件发生 id 冲突时使用命名空间。manual 无需 check/test_name；auto 必须关联同仓库 report: junit 的实际检查与精确 classname::name。

导入会记录原件及规范化文件摘要、来源 qa/ai、实际审阅者。只有 `--reviewed-by` 才标记 reviewed，否则 draft。审阅是实际业务/测试判断，参数不是身份认证。原件数量、导入数量、重复和解析失败由 Agent 对账；核心不证明原件被完整解析。

## Agent 命令

```text
kit cases draft --workspace <工作区> --repo frontend
kit cases import --workspace <工作区> --input <规范化.yaml> --original <原件任意格式> --source qa
kit cases import --workspace <工作区> --input <规范化.yaml> --original <原件> --source qa --reviewed-by <实际审阅者> --expect <最新revision> --apply
```

draft 只返回验收种子，不保存、不运行；Agent 必须细化可执行步骤与场景。导入默认预览；已有 id 必须显式 --replace，未涉及用例保留。导入按既有变更流程使对应确认失效，核对新增验收后使用真实依据 confirm。CSV/YAML 是核心支持的交换格式，不是对用户上传文件的限制。

## 用户明确要求浏览器操作测试

用户说“打开浏览器测试”“操作页面验证”“用浏览器模式测试”，或项目验收明确要求页面交互时，必须走实际浏览器操作；此要求优先于默认的分层测试选择，不能用 API、单元测试、静态代码审查、只生成脚本或只运行无头测试替代。

1. **发现并调用技能**：读取当前环境的技能目录，优先使用用户指定且适用的浏览器技能；否则选择可执行页面验证的技能，实际读取其 SKILL.md 并遵循操作协议，再调用配套浏览器工具。某些环境提供 verification、browser 或 Playwright 相关技能，但不能假定名称、安装路径或能力固定，也不把某个平台作为套件依赖。只有工具而无技能时，明确说明缺口；可用工具完成已授权验证，但不得声称已调用技能。技能和工具均不可用时标记阻塞，不改用 API 冒充完成。
2. **打开真实页面**：核实本地/dev 地址、服务身份和版本，使用用户指定浏览器或当前环境支持的可见浏览器会话，实际打开目标页面。仅有无头执行能力时，说明尚未满足可见浏览器要求，不能静默降级。
3. **按用例操作**：从实时页面状态定位元素，执行实际点击、输入、选择、导航等步骤，并观察操作后的页面结果。只打开首页或只截一张图不算业务流程通过。覆盖本次要求的正常、异常和应保持不变的行为，不扩展成所有功能的完整 E2E。测试环境中的提交、删除等动作仍须符合已授权的数据范围。
4. **记录真实证据**：逐条记录用例、环境/版本、入口、关键操作、预期与观察结果，以及必要的本机截图/trace 引用；具备能力时结合控制台、网络及服务日志排障。缺少某项观测能力须说明，不能编造。记录实际使用的技能和浏览器工具，输出中不携带令牌、凭证或客户数据。
5. **回写结果**：交互式 Agent 操作没有 JUnit 时，按现有 manual 观察型用例记录实际执行者与证据说明；manual 在这里指观察记录，不代表必须让用户代测。已有 auto 用例不能直接用 manual 命令覆盖通过：保留其自动验证，并按变更流程增加所需浏览器观察用例。只有真实测试框架生成本次逐条 JUnit 才走 auto。未操作、环境不可达、登录受阻的用例保留未通过/blocked；需要用户接手时指出具体步骤。

结束按 [进度反馈协议](progress-feedback.md) 报告实际测试了哪些页面和动作、通过/失败/未执行项及下一步。调用过技能不等于已操作浏览器，操作过浏览器也不等于业务验收全部通过。核心记录观察证据，但不独立证明 Agent 是否真实操作；实际工具调用与观察由执行 Agent 负责。

浏览器工具选择、局部观察、会话复用和测试过程录像按 [效率与证据协议](browser-testing.md) 执行。

## 测试发现缺陷后的修复与续测

测试开始前记录本轮模式：默认“仅测试”，只有用户在开始前明确要求“遇错尝试修复”才为“测试并尝试修复”，保留真实授权原话和范围。以往的开发授权、“继续测试”或本轮未说明不能推断修复许可；不要为开始普通测试强迫用户选择模式。

默认遇错先记录用例、步骤、预期/实际、环境/版本、证据及问题编号。仅做必要只读分析，不改业务代码、断言、用例或环境配置来解决问题。检查后续用例依赖和数据状态：能回到已知前置、且在既有测试授权内安全切换页面/重置测试数据时，尝试跳过失败场景继续独立用例；失败项仍为 failed，依赖它的项标 blocked，未运行项标未执行。跳过流程不等于删除用例或算通过。

若公共登录/服务不可用、共享状态污染、写入结果不明或无法恢复到可信前置，停止本轮，列出具体停点和未执行原因，结束录屏并输出测试报告及问题分析；不尝试修复、不反复重试副作用不明的操作。局部问题只阻挡依赖它的场景，报告未完成测试不能称为整体验收通过。

测试途中用户后来要求修复时，先结束并报告当前测试轮，记录新授权后开始新的修复/复测轮，关联原问题。授权修复仍不允许扩大业务范围或跳过需求变化二次确认。

以下修复步骤**仅在本轮开始前已有明确遇错修复授权时执行**；默认仅测试模式不得进入：

1. **回到开发流程**：读取原始需求、正式用例、项目规则和实际参考实现，调用 flow-implement；核对行为约定、复用、风格、调用方影响及必须保留的行为。关联失败用例和修复任务，补最小必要的回归覆盖，不顺手重构。doing 任务继续原快照；原任务已经 done 时通过 flow-change 增加关联修复任务或按正式变更流程调整，不能直接修改 status 或重复 start 已完成任务。新的业务歧义或超出授权的范围才询问。
2. **修复并检查**：按项目既有实现方式修复，先运行相关单元/组件/API 检查，再按 flow-code-review 阅读真实差异，核对需求、代码规范、复用与影响。浏览器回归尚未执行时保留待验证状态，不提前记录全部通过或 finish。
3. **本地真实重启**：修复完成后，按项目已核实的启动方式重启相关本地应用/服务；需要构建的先重新构建。热更新、页面刷新或端口开放不能代替重启和就绪检查。确认工作目录、服务/进程身份、健康状态以及正在运行新代码，再继续测试。使用测试框架生命周期管理也须确认实际重启，不能因 reuseExistingServer 而复用旧实例。只操作属于本项目且在授权范围内的服务；共享或归属不明的进程先核实，不按端口批量杀进程。重启失败先处理环境问题，不对业务结果下通过结论。没有常驻服务的纯脚本/库项目注明不适用，并启动新的测试进程。
4. **重测后续测**：先从必要前置重新执行原失败用例，再测受影响回归场景；通过后从记录的停点继续剩余测试，不能直接跳到后续步骤。原要求是浏览器操作时，重新调用适用技能和工具，在重启后的页面实际操作，接口通过不能替代。注意测试数据和会话是否需要恢复，不盲目重放副作用不明的提交。再次失败则回到定位修复，不无依据重复同一操作。
5. **刷新交付证据**：代码改变后重新获取受影响的测试和审查证据，不能沿用旧 passed；审查无未解决问题且回归证据齐全后才 finish。反馈缺陷原因、修复、重启/就绪结果、复测和剩余用例；真实阻塞时说明具体缺口与下一步。

若失败发生在 dev，本地修复、重启及验证后，dev 用例仍保持待复测；只有修复版本按既有发布流程部署且重新核实版本后，才继续 dev 测试。没有部署授权时说明等待修复版本，不自动部署，也不把本地结果冒充 dev 结果。

## 本地与 dev 环境

项目配置示例（名称、路径、命令由 Agent 按实际项目调整）：

```yaml
runtime:
  environments:
    local:
      kind: local
      base_url: http://127.0.0.1:3000
    dev:
      kind: dev
      base_url: https://dev.example.test
      deployment_id: verified-build-123
      required_env: [TEST_API_TOKEN]
  checks:
    order-api-local:
      repo: frontend
      argv: [npm, run, test:api]
      environment: local
      report: junit
      timeout_seconds: 180
      requires: []
    order-api-dev:
      repo: frontend
      argv: [npm, run, test:api]
      environment: dev
      report: junit
      timeout_seconds: 180
      requires: []
```

每个检查固定一个环境，避免运行时静默切目标。同一业务用例需要两环境验收时，分别建立稳定用例 id、check，保留相同 external_id。dev 检查用于部署验收用例，不能配置在本地实施任务的 checks 中替代本地验证。

运行时注入 KIT_BASE_URL、KIT_ENVIRONMENT、KIT_ENVIRONMENT_KIND、KIT_JUNIT_PATH；账号只通过现有进程环境传入，配置仅写变量名。脚本必须实际读取这些值；套件无法限制任意子进程忽略配置或访问其他地址。审核测试脚本与目标是 Agent 的责任。

本地服务由项目测试框架管理生命周期。Playwright 示例见 [配置模板](../examples/testing/playwright.config.ts)，利用 [webServer](https://playwright.dev/docs/test-webserver) 启动并等待服务；已有服务须确认身份，不能仅因端口开放就复用。dev 不执行本地启动命令。API 用例可以使用 [request fixture](https://playwright.dev/docs/api-testing)，不必启动浏览器。其他项目复用 pytest/JUnit 等框架，不强制换技术栈。

```text
kit run --workspace <工作区> --check order-api-local --expect <最新revision>
kit run --workspace <工作区> --check order-api-dev --ready environment:dev --expect <最新revision>
```

dev readiness 是实际核实目标、部署版本、访问权限与数据边界后由 Agent 记录的事实；不能把配置的 deployment_id 当自动探测结果。远端重新部署后需更新版本并重跑。当前不自动部署、登录、启动 VPN 或清理远端数据。

## 逐条结果与证据

测试框架必须在 KIT_JUNIT_PATH 写入本次新 UTF-8 JUnit XML，套件每次分配唯一临时路径。配置方式参考 [Playwright reporters](https://playwright.dev/docs/test-reporters)。只匹配精确 classname::name；首次接入检查真实报告命名，不猜测。

零测试、报告缺失/无效、失败、映射缺失、跳过或重复名称都不能产生整项通过证据。整项报告中的跳过或重复名称即使没有用例映射，也不能让任务级检查通过。重复名字（包括重试或多个浏览器）需要拆分检查或唯一命名，不选择最后一次成功掩盖失败。任一测试 failure/error 使该检查失败，即使命令退出码为零。

证据仅保留映射结果、数量、报告摘要、代码及环境摘要和部署版本，解析后删除临时原始 XML。截图、trace、测试框架自行生成的文件仍由项目配置忽略并管理；不得把原始响应、密码或截图内容复制进共享证据。命令原始输出默认不落盘。

旧版没有 JUnit 映射的检查仍按命令级验证兼容；新导入的自动化用例强制使用逐条报告，不能声称旧检查已有逐条覆盖。

跨轮次执行方法与证据复用按 [测试复用协议](test-reuse.md) 处理，记录落在业务项目，不能把旧结果冒充本轮执行。
