# 编写代码和注释

改代码时先读该仓库的 `AGENTS.md`、格式化配置和邻近文件。仓库里已有的写法优先于本页。本页只补仓库没写的部分。

这些约定来自常见工程实践：改动保持小、名字表达意图、注释解释为什么而不是把下一行翻译一遍、提交前用项目自己的检查命令。

## 改动范围

- 只改当前任务点名的文件。
- 新代码靠近仓库里同类功能的写法：目录、命名、错误处理、日志。
- 不顺手重排无关格式，不删看起来没用、但这次任务没提到的代码。
- 名字按仓库已有风格。没有风格时，名字要能看出是什么，少用 `data`、`temp`、`flag` 这类空词。

## 注释写什么

写注释的目的，是让下一个人知道代码本身看不出来的事。

要写的：

- 为什么这样写，以及不那样写会怎样。
- 业务上的限制、外部系统的怪癖、时区、单位、精度。
- 会改到外部状态的副作用：写库、发消息、删文件。
- 看起来像笔误、其实是故意的分支。

不写的：

- 把下一行代码用中文或英文再说一遍。
- 每个文件开头一段长说明。
- 把不要的代码注释掉留在文件里。不要的代码直接删。
- 没有需求编号、也没有人认领的 `TODO`。

示例：

```text
不写：// 把 count 加 1
要写：// 库存按件计数，接口返回的是箱数，这里乘以每箱件数
```

语言不限。项目若规定注释只用英文，或必须写在函数声明上，跟项目走。

## 函数和错误

- 一个函数做一件事。名字已经说明白的，不必再写注释。
- 失败时沿用仓库的方式返回错误或抛出异常，不要在新代码里换成另一种风格。
- 不要吞掉错误后继续装作成功。

## 检查

任务里的验证命令用仓库已有的格式化、静态检查或测试。没有这类命令时，在任务上写明「仓库未配置」，不要临时加一套新的格式化工具。
