# 文档谁说了算

写计划和改代码时按这张表。上面的一行不能被下面的一行悄悄改掉。

## 严和松

套件适应仓库现状。只有会造成不可逆损害或假结论的地方才卡住。

| 严 | 松 |
|----|----|
| 不覆盖、不删除已有需求材料 | 父目录可以是 git 仓库，也可以只是包住前后端的文件夹 |
| 不把已经入库的文档写进 `.gitignore` | 文档可以在当前仓库、单独文档库或共享目录。目录名用仓库里已有的 |
| 密钥不落盘。不 force push，不改 git config，不跳过钩子 | 没有录屏时，从已有 Spec、链接或代码开始 |
| 没看到命令输出，不能写成测试通过 | 文件不必先改名为 `01` 到 `07`。先摘录进 `02-sources.md` |
| 问题没确认时，不把未决事项写成最终需求或计划，也不按这个范围改业务代码 | 分支名和主干跟仓库已有规则。没有规则时才用套件的 `feature/{id}` |
| 业务仓 `AGENTS.md` 更严时，按业务仓，不改写那份文件 | 规范还没确认时，可以起草背景、接上已有需求、整理材料。建分支和改代码之前再确认 |

## 谁说了算

| 文档 | 角色 |
|------|------|
| 各代码仓的 `AGENTS.md`、`README` | 项目红线：命令、分支、禁止的依赖和已知陷阱 |
| `05-impact.md` | 代码事实：路径和现状。写「要改」的路径必须在仓库里存在；写「新增」的路径可以还不存在 |
| `04-requirement.md` | 确认后的范围，含「不做」。开发顺序和改动不得超出这里 |
| `06-plan.md` | 执行清单。任务若超出 `04` 的「不做」，标成不执行，不要做 |
| `01-meeting.md`、`02-sources.md` | 来源。和已确认的 `04` 冲突时，以 `04` 为准；还没确认时，写进 `03-questions.md` 并停住 |
| `07-testcases.md` | 怎么验收。对不上 `runtime` 里已有命令的条目标 `manual` |

三份核心文件是 `04-requirement.md`、`05-impact.md`、`06-plan.md`。做实现时缺任何一份，或正文少于一两句，就停止，不要凭会议记录补需求。

`project.local.yaml` 的 `current` 为空，且需求目录多于一个时，先问用户做哪一条，不要自己选第一个。

本机若有 `codegraph` 命令，对照代码时可以先用它看调用链，再用文件内容核对。没有这条命令就直接读代码，不要为此停下来，也不要在套件里安装它。
