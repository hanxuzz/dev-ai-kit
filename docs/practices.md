# 每个节点要满足什么

技能写文件时对照本页。来源是公开、常用的做法，套件只取能直接写进文档的那几条。

| 做法 | 用在哪 |
|------|--------|
| 一条需求只说一件事，并且能判断有没有做对（ISO/IEC/IEEE 29148 里对单条需求的要求） | `04` 的 `R` 编号 |
| 验收写成「给定 / 当 / 则」（行为驱动开发里的 Given / When / Then） | `04` 的验收列，`07` 的步骤和期望 |
| 条目要能单独理解和测试（INVEST 里的可测试、范围不要糊成一大段） | 从会议纪要拆到 `R` |
| 准备好再写计划：范围已确认、验收写得出来、要改的路径已核对（就绪定义） | `flow-plan` 开工前 |
| 做完要有证据：勾选、验证命令的本次输出（完成定义） | `flow-implement`、`flow-test` |
| 编号能从说法追到改动再追到用例 | `M` → `S` → `Q` → `R` → `C` → Task → `T` |
| 决定单独记一笔：日期、背景、决定、后果（架构决定记录的简表） | `team/decisions.md` |

编号：

| 编号 | 出现在 |
|------|--------|
| `M1` | `01-meeting.md` 里的一条说法 |
| `S1` | `02-sources.md` 里的一份资料 |
| `Q1` | `03-questions.md` |
| `R1` | `04-requirement.md` 里确认后的一条需求 |
| `C1` | `05-impact.md` 里的一处改动 |
| Task 1 | `06-plan.md` |
| `T1` | `07-testcases.md` |

写不下去时的处理：

- 一句话里有两件要做的事：拆成两条。
- 写不出「则」：不要编成 `R`，留在 `Q`。
- 「做得好一点」这类不能判断对错的句子：留在未定或 `Q`。
- 某个 `R` 没有对应的 `T`：在用例里写明不测的原因，不要假装覆盖了。
