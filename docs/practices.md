# 交付标准

每条范围内 R 必须有来源、可观察验收、任务承接和用例覆盖。明确不做的内容不能变成任务。
编号保持稳定，不因重排任务重新编号：来源 S/M/Q → 需求 R → 任务 TASK → 用例 T → 证据编号。

## 开工

来源已足够支撑本次范围；疑问已澄清；规格、影响和方案一致；当前版本已确认；团队规范及分支符合要求；任务依赖完成。
结构校验不能证明业务语义正确。Agent 必须核对范围、不做事项、影响分析和原始材料，不能为了过校验填占位句。

## 完成

任务 start 保存修改前代码快照；finish 要求代码范围未超出声明、当前版本验证通过。发现其他人的并行修改时解释冲突，不删除或回滚别人的文件。
用例的 check 必须真实覆盖对应验收。只有全局 `npm test` 但不知道覆盖哪个 R 时，不得直接把 R 标自动覆盖；补人工验收或选择项目已有针对性命令。
最终 complete 要求所有任务完成、所有用例有最新代码通过证据，以及用户明确验收。

## 需求变更

先记录理由及受影响的 R、任务、接口和测试；change 或 prepare 使旧确认失效。复核后 confirm 绑定新版本。
当前实现保守地重新打开该需求全部任务并使旧证据失效，保留历史，不猜测影响传播。确定无关的代码无需重写，但需要重新核对和验证。

## 交接

在 status.handoff 记录未验证修改、当前环境、外部待办和下一动作；不能把交接说明当验证证据。
接续先读 status --full、Git 现状及材料版本，不重复 start 已进行任务，不重跑不确定副作用的命令。
